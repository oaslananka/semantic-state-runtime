# Install the Semantic State Runtime Developer Preview

**Status:** `semantic-state-runtime@next` is publicly available on npm as a Developer Preview. It is **not** a stable consumer release, an MCP Registry listing, or a hosted service.

## Install from npm (recommended first run)

Requirements: Node.js 24.12+ and npm. No source clone or API key is necessary for the local MCP runtime.

~~~bash
npm install -g semantic-state-runtime@next
ssrl-demo-init ./ssrl-example
ssrl-node --version
~~~

The initializer creates a new synthetic **read-only** workspace with `./ssrl-example/ssrl.config.json`; it refuses an existing destination and does not search personal files. Configure your MCP client to launch `ssrl-node` with the **absolute path** of this config file. Request `context.compile` for `Project Atlas deadline`; the authorized example yields `2026-11-20`.

This flow was independently tested against the actual published npm package on Windows and Linux using synthetic data and real MCP calls. It is **not** a human end-to-end acceptance result, a cloud sync test, or permission to enable real-data writes.

Alternatively, you can install the compiled **stdio MCP server** from source into a separate final directory without publishing another package. The installation bundles production dependencies needed to run it; only the installation step needs the pnpm workspace. The runtime needs Node.js 24.12+ and an explicit SSRL configuration.

## Source-based installation

Requirements on the build machine: Node.js 24.12+, pnpm 12.14.0 (via Corepack or an existing pinned pnpm installation), and Git.

~~~bash
git clone https://github.com/oaslananka/semantic-state-runtime.git
cd semantic-state-runtime
pnpm install --frozen-lockfile
pnpm preview:install -- ../ssrl-preview-runtime
node ../ssrl-preview-runtime/dist/cli.js --help
~~~

The command builds the source and deploys only production dependencies to **one new directory**, then checks the installed CLI.
The installed folder includes its own **MIT LICENSE notice** and the
local runtime/configuration guide under docs/. Select the **final directory** deliberately. The installer refuses to overwrite a path that already exists, refuses destinations inside the source checkout, and does not delete existing files.

**Windows:** pnpm currently emits absolute directory junctions in this preview deployment. The installed runtime works at its original destination but **moving or renaming the directory can break it**. Choose the final path first; for a different path, run the preview installation into another *new* directory. Do not promise a relocatable Windows ZIP.

**Linux:** a separate clean-clone acceptance on Linux verified that the deployed CLI could run after a directory rename; the repo's preview smoke test additionally checks the actual MCP tool calls after relocation. This does not establish that the same artifact can run on another OS/architecture.

## Connect an MCP client

The installed executable is:

~~~text
node /absolute/path/to/ssrl-preview-runtime/dist/cli.js /absolute/path/to/your-ssrl.config.json
~~~

Use this command and arguments as your MCP client's **stdio server** configuration. The example shows POSIX-style paths; use the equivalent final directory on Windows.

The config file is **not automatically generated for real personal data**. Follow the [explicit local config contract](local-node-runtime-v1.md) to select the Markdown directories, canonical entities, trusted provider, field policies, and principal scopes you actually authorize. The CLI does not search your disk on its own. For a read-only client, avoid granting write operations.

No model key is required for the MCP server or its deterministic test. A particular chat application may require its own inference account.

## Independent acceptance

After a normal repo build, run:

~~~bash
pnpm test:preview-install
~~~

The offline smoke test creates its **own disposable** installation, checks existing-target refusal, and uses the installed runtime rather than the checkout's CLI for real MCP calls. It verifies source authority, `context.compile`, plan/apply permissions, denial of hidden evidence, stale-proposal rejection, and restart persistence. On Linux it reruns the MCP test after relocating the installation. On Windows it verifies the original final location, not relocation.

The deployed manifest may include `file:///` references generated by pnpm. The installation is **already provisioned**, so do **not** run `npm install` inside it or claim it is a valid distributable npm tarball. This is a step toward a standalone package, not the packaging/release acceptance itself.

**Still unverified:** clean human-user setup with personal files and live multi-device replication. The `0.1.0-beta.2` npm release has **signed SLSA v1 provenance** from GitHub Actions OIDC, and its registry installation and synthetic MCP session were separately verified on Windows and Linux. These checks do not establish readiness for production user data.

## Local npm tarball preview (unpublished)

For development and packaging acceptance, you can build a self-contained tarball without adding a hosted service or publishing to a registry. The package is intentionally marked **private** and cannot be published as-is.

~~~bash
pnpm install --frozen-lockfile
pnpm preview:pack -- ../ssrl-npm-preview
cd ../ssrl-npm-preview
npm pack
~~~

The generated directory contains a bundled stdio CLI, MIT license, and the local runtime configuration guide. It does **not** include the pnpm workspace or `file:///` runtime dependencies. The local tarball is an experimental distribution candidate, not a supported npm release.

The source repository's `pnpm test:preview-pack` runs `npm pack`, installs the resulting tarball **offline into a different directory**, and checks `--help`, `--version`, and real policy-scoped MCP stdio tool calls. This test must pass on the exact PR head before any public distribution is considered.

The released package name and cross-platform synthetic installation were verified against the public npm registry. An independent human first-run and an MCP Registry listing are still outstanding; this does not establish production-readiness or a stable release.

## Public npm prerelease packaging (maintainers)

The source repository remains **private as an npm workspace**. To reproduce a candidate release **locally** from the current source manifest:

~~~bash
pnpm install --frozen-lockfile
pnpm release:pack -- ../ssrl-release-candidate
cd ../ssrl-release-candidate
npm pack
npm publish --dry-run --tag next --access public
~~~

The commands above **do not publish** another registry package. The released Developer Preview is distributed via the explicit `next` tag; the normal `preview:pack` output stays `private: true`. Both include the MIT notice and bundled third-party license notices. Avoid unversioned installs or treating this beta as stable.

### First user experience

After installing `semantic-state-runtime@next`, run `ssrl-demo-init ./ssrl-example` to create a **new**, synthetic, read-only directory; this refuses overwrites and never scans existing user files. Connect an MCP stdio client with `ssrl-node ./ssrl-example/ssrl.config.json` and ask it to call `context.compile` with task `Project Atlas deadline`. The response should contain the authorized sample date `2026-11-20` without private data. For personal projects, review the detailed configuration guide before mapping any real files or enabling writes.

The initial npm registry publication was verified under npm account `oaslananka`; the real package was downloaded and tested from the registry on Windows and Linux. **Provenance/attestation is not asserted for the manual first `0.1.0-beta.1` release**; the later OIDC beta.2 has signed provenance, but a stable consumer release has not been validated.

## Subsequent npm releases with GitHub Actions OIDC

The single release workflow is `.github/workflows/publish.yml`, with
**manual dispatch from `main`**. In the npm package's Trusted Publisher
settings, select **GitHub Actions** with owner `oaslananka`, repository
`semantic-state-runtime`, workflow filename **`publish.yml`** (filename only),
and **no environment name**. Enable both **Allow npm publish** and
**Allow npm dist-tag**. The connection cannot be edited after creation;
a replacement requires deleting the old connection. See the
[official npm Trusted Publisher documentation](https://docs.npmjs.com/trusted-publishers/).

This workflow uses GitHub-hosted Ubuntu, `id-token: write`, npm 12.2.2,
no npm token, and a strict `main` branch / repository identity guard.
Enter a **new**, unclaimed prerelease version in the workflow's required `version` field
that exactly matches `packages/node-app/package.json` after the usual
PR checks and merge. The workflow rebuilds, runs offline MCP packaging
acceptance, performs npm publish dry-run, then publishes under `next`.
Never use it to overwrite an existing immutable version. Trusted OIDC
publishing from this public repository should attach npm provenance;
verify it for each new version rather than assuming it exists.

**First-release tag limitation:** npm set `latest` to `0.1.0-beta.1`
during the inaugural release, while the verified OIDC release points `next`
to `0.1.0-beta.2`. npm rejected the attempted `latest` deletion with
HTTP 400 (`Dist-tag request rejected`). The workflow does not offer that
unsuccessful operation. **Always install `semantic-state-runtime@next`**
for the latest Developer Preview; unqualified installs currently resolve
to the older beta.1. Do not move `latest` to an unverified stable version.

**Do not configure an npm token in GitHub secrets** for this workflow.
Trusted Publisher OIDC is tied to the exact GitHub workflow filename.
Changes to the workflow name in npm require a replacement trust connection.
